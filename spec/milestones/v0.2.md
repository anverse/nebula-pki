# Milestone v0.2 — encryption, CA cert distribution, rekey, the `cert` rename, CA references, and explicit trust bundles

End state: an operator can configure `encryption "sops" {}` and have every private key written sops-encrypted (via `.sops.yaml` discovery or inline recipients); use `encryption "external" {}` to plug in any command-line encryption tool; run `nebula-pki rekey` to re-encrypt all key files when recipients change; declare `link_crt` on a `ca` block to place git-committable symlinks of the CA certificate into any output directory that needs it; declare per-certificate `cert` blocks (renamed from `host`); reference CAs terraform-style (`ca = ca.next`); and declare a `trust_bundle` block that states trust membership explicitly via `ca_refs`, fans the bundle out via its own `link_crt`, and replaces the `archived` flag.

Versioning: iterations between v0.1.0 and the v0.2 cut ship as `v0.1.x` tags. Each is a real, installable release.

The encryption backend shells out to the `sops` CLI rather than embedding the `getsops/sops` Go library. This keeps the binary lean (no transitive AWS/GCP/Azure SDKs) and defers sops release tracking to the operator. See [ADR-003](../adr/003-encryption-strategy.md).

The config naming decisions each carry their own rationale: `host`→`cert` in [ADR-024](../adr/024-rename-host-to-cert.md), the `ca.<label>` reference form in [ADR-025](../adr/025-ca-references.md), and the `trust_bundle` block / `ca_refs` field in [ADR-026](../adr/026-trust-bundle-block.md).

## Acceptance criteria for v0.2.0

### SOPS encryption (`encryption "sops"`)

- All CA private key files (generate mode) and cert private key files are written sops-encrypted with the configured recipients.
- Empty block (`encryption "sops" {}`) — the `sops` binary performs its standard upward search for `.sops.yaml` from the temp file's directory (placed in the same directory as the output file); no inline recipients required.
- Inline recipients (`age`, `pgp`, `kms`, `gcp_kms`, `azure_kv`, `hc_vault_transit`) take precedence over `.sops.yaml` for files written by nebula-pki — same precedence rules as `sops --encrypt --age ... --pgp ...`.
- `shamir_threshold` and `config` (explicit `.sops.yaml` path) are honoured when set.
- `output_suffix` (default `".enc"`) appended to key file names on disk; the manifest records paths **with** the suffix so it exactly describes what is on disk.
- Only **private key files** are encrypted. `.crt` certificates, QR PNGs, the manifest, and the trust bundle are never encrypted and never suffixed.
- **Decryption on reuse** — when a CA key was previously written as `.key.enc`, the tool decrypts it in-memory by shelling out to `sops --decrypt --input-type binary --output-type binary`; no plaintext temp file is written to disk. The `sops` binary must be in PATH for any reconcile that signs certs under an encrypted CA key.
- **Idempotency** — a re-run against an unchanged config produces no key-file writes; existing encrypted key files are left untouched.
- **Recipient-mismatch warning** — when the `recipients_sha` stored in the manifest for an existing encrypted key file differs from the hash of the currently configured recipients, the CLI prints a warning on every run until `nebula-pki rekey` re-encrypts the file. Applies only when both sides have a non-empty hash (i.e., inline recipients were configured for both the stored and current run); `.sops.yaml`-only mode emits no mismatch warning.

### External encryption backend (`encryption "external"`)

- `encryption "external" { encrypt_command = [...], decrypt_command = [...] }` — invokes operator-supplied commands to encrypt and decrypt key files. `{{.InPath}}` / `{{.OutPath}}` are substituted with absolute temp-file paths at invocation time; see ADR-023 for the full protocol.
- `output_suffix` behaves identically to the sops backend.
- Decryption on reuse: when a CA key exists at a suffixed path, the `decrypt_command` is invoked; decrypted bytes are piped through stdout into memory, no plaintext temp file.
- Recipient-mismatch warning: when a SHA-256 of the `encrypt_command` slice stored in the manifest differs from the current config's hash, warn on every run until `nebula-pki rekey` is executed.

### Reencrypt subcommand (`nebula-pki rekey`)

- `nebula-pki rekey` — reads every managed key file that the manifest records as encrypted, decrypts it using the backend and credentials that produced it, and re-encrypts it with the current backend and recipients. Atomic writes (temp-then-rename); aborts on first error leaving previously written files intact.
- `--dry-run` flag supported (prints what would be re-encrypted, no writes).
- `--force` flag — re-encrypts all managed key files regardless of whether a mismatch is detected. Intended for external-backend cases where the encryption behaviour changed without the tracked command string changing.
- After a successful `rekey`, the mismatch warning is cleared (manifest `recipients_sha` updated).
- Works across both `sops` and `external` backends (old and new backend may differ, enabling migration between backends).

### CA cert links (`link_crt`)

- `ca "<label>" { link_crt = ["dir/a", "dir/b", ...] }` — creates a symlink at `<dir>/<symlink-name>` in each listed directory, pointing to this CA's certificate file.
- Symlink name follows the CA cert naming: `<label>.crt` by default; if `out_crt` is set, the basename of the resolved `out_crt` path.
- Symlink targets are **relative** paths computed via `filepath.Rel`, so they survive being committed to git and cloned to a different absolute path.
- Parent directories are created if they do not exist.
- **Idempotency** — correct target → no-op; broken or wrong target → recreated; regular file at the path → error (never clobbered).
- **Stale link cleanup** — when a path is removed from `link_crt` between runs, the old symlink is deleted. If a regular file now occupies the path, the tool prints a notice and skips deletion.
- The manifest records each symlink under `cas.<label>.links` as `{"path": "...", "target": "..."}`.

### `cert` block (renamed from `host`)

- Per-certificate declarations use the `cert` keyword: `cert "app_01" { name = "...", networks = [...], ca = ca.next, ... }`. See [ADR-024](../adr/024-rename-host-to-cert.md).
- Only `cert` is accepted; a leftover `host` block fails with the generic HCL "Unsupported block type" error (experimental stage, no targeted rewrite error, see [ADR-007](../adr/007-schema-evolution.md) 2026-09-26 amendment).
- The block label is still the manifest key; all fields (`name`, `networks`, `groups`, `output_dir`, `out_crt`, `out_key`, `in_pub`, `ca`, `renew_before`, …) keep their names and semantics.
- The rename goes end to end, with no migration path: manifest `hosts` → `certs` (no `schema_version` bump), default artifact directory `out/hosts/` → `out/certs/`, code identifiers, all CLI output, and every ADR (including renaming ADR-009/017/020 files).

### CA references (`ca.<label>`)

- `cert.ca` takes a traversal reference: `ca = ca.next`. A quoted string label is rejected like any other non-reference expression (hard switch, no dual-accept window, no migration path). See [ADR-025](../adr/025-ca-references.md).
- References are decoded via `hcl.AbsTraversalForExpr` — no eval context; `ca.next` is syntax, never a value, so it cannot leak into interpolation.
- Traversal shape is exactly `ca.<label>`; the index form `ca["<label>"]` is rejected. A foreign root gets an "unknown reference root" error; every other malformed value gets the regular reference error. All reference errors carry the expression's source range. `ca = null` counts as omitted.

### Explicit `trust_bundle` block

- `trust_bundle "<label>" { ca_refs = [ca.a, ca.b], path = "...", link_crt = [...] }` — exactly one `trust_bundle` block allowed; `ca_refs` is a non-empty, duplicate-free list of CA references; membership is explicit. See [ADR-026](../adr/026-trust-bundle-block.md).
- No `trust_bundle` block → **no bundle emitted** and no `trust_bundle` manifest record. The bundle is fully declarative — there is no implicit "every declared CA" bundle (supersedes ADR-016's always-emit). A stable `pki.ca` path is obtained by declaring a `trust_bundle` up front (even single-member).
- The `archived` flag is **removed** (no longer accepted; generic HCL error). Its signing ban becomes validation: **when a `trust_bundle` is declared**, every cert's resolved signing CA must be a member of it; `default = true` on a non-member CA is an error. With no `trust_bundle` block there is no signing constraint.
- `storage.trust_bundle_file` is **removed** (no longer accepted; generic HCL error). The bundle path is `trust_bundle.path` (default `<out_dir>/ca/bundle.crt`).
- `trust_bundle.link_crt` fans out the bundle with ADR-021 semantics; symlink filename is the basename of the bundle path (`bundle.crt` by default). **Symmetric symlink-path uniqueness**: no two `link_crt` sources (any `ca` block or the `trust_bundle`) may write the same `<dir>/<filename>`; sharing a directory with different filenames is fine. Validated CA-vs-CA, CA-vs-bundle, and bundle-vs-CA.
- Manifest: `trust_bundle` gains `label` and `links`; the CA record's `archived` field is removed; no `schema_version` bump.

## Decisions

### D-1: What gets encrypted

Only private key files (`.key`, written as `.key<suffix>`) are encrypted. Public certificates (`.crt`), QR PNGs, the trust bundle, and the manifest contain no private material and are left plaintext.

See [ADR-003](../adr/003-encryption-strategy.md#what-gets-encrypted).

### D-2: Sops via CLI subprocess, not Go library

`encryption "sops"` shells out to the `sops` binary rather than embedding `getsops/sops/v3`. This keeps the binary lean (no transitive AWS/GCP/Azure/Vault SDKs), means sops version upgrades are the operator's concern, and is consistent with how the `external` backend works. Operators who choose `encryption "sops"` already have sops installed.

See [ADR-003](../adr/003-encryption-strategy.md).

### D-3: No automatic re-encryption on recipient change

Changing recipient fields between runs does **not** trigger automatic re-encryption. Key files are only (re-)written when the key material itself changes. When the manifest-stored `recipients_sha` differs from the current config's hash, a persistent warning is emitted; the operator resolves it explicitly with `nebula-pki rekey`.

See [ADR-003](../adr/003-encryption-strategy.md#recipient-mismatch-warning).

### D-4: Manifest key paths include encryption suffix

The manifest stores artifact key paths **as they exist on disk**, including the encryption suffix (e.g., `out/certs/app_01.key.enc`). The `encryption.suffix` field in the manifest allows the tool to locate encrypted files even if `output_suffix` is later reconfigured. No schema-version bump is needed.

### D-5: `external` backend ships in v0.2

The `external` backend gives operators an escape hatch for any encryption tool: custom KMS wrappers, standalone `age`, anything. Since the subprocess architecture is already established for the sops backend, the implementation is a thin layer. A good tool delivers its escape hatch by day one.

See [ADR-006](../adr/006-storage-backend-extensibility.md).

### D-6: `link_crt` uses a list of directories; symlink name follows CA cert filename

`link_crt` is a list of **directories**. The symlink filename is derived from the CA cert filename (`<label>.crt` or `out_crt` basename), reusing existing path logic.

See [ADR-021](../adr/021-ca-cert-links.md).

### D-7: Symlinks are always relative

Symlink targets are computed as relative paths via `filepath.Rel(linkDir, caAbsCertPath)`. Absolute symlinks break after `git clone` to a different path.

See [ADR-021](../adr/021-ca-cert-links.md).

### D-8: CA references are traversals, not strings — and `cert.ca` hard-switches

`ca.<label>` is decoded as an HCL traversal (`hcl.AbsTraversalForExpr`), the Terraform `depends_on` technique. No eval context. String labels in `cert.ca` are rejected immediately — experimental stage, no dual-accept window, no migration path.

Detail decided 2026-10-02: one spelling only (`ca["x"]` rejected), source ranges on every reference error, `ca = null` counts as omitted, the JSON Schema describes the field as a `ca.<label>` string pattern, and docs show only the reference form with no notes about the string syntax.

See [ADR-025](../adr/025-ca-references.md).

### D-9: The `trust_bundle` block owns the trust axis only; `default` stays on `ca`

Signing default and trust membership are the two distinct rotation axes (ADR-016). `default` decides which CA signs each cert — a signing concern with no relation to the trust bundle — so the `ca` declarations are its natural home. The placement also keeps the deferred multiple-bundles future open: a per-bundle default would be ambiguous with more than one trust set, a default among the CA declarations is not. Moving the default into the bundle was considered and rejected.

See [ADR-026](../adr/026-trust-bundle-block.md), considered alternative A.

### D-10: `archived` and `storage.trust_bundle_file` are removed, not deprecated

Both effects of `archived` are subsumed: bundle exclusion by omission from `trust_bundle.ca_refs`, the signing ban by the "signing CA must be a bundle member" validation. `trust_bundle_file` moves to `trust_bundle.path` — the explicit bundle owns its own path, and a `storage`-level override would be a second home for one setting. Removals ship directly in v0.1.9 under the experimental-stage amendment to ADR-007 — no deprecation window, no schema-version block, no targeted rewrite errors.

See [ADR-026](../adr/026-trust-bundle-block.md), "Deviation from ADR-007" and considered alternative D.

### D-11: No implicit bundle — the trust bundle is fully declarative

Absent a `trust_bundle` block, **no** bundle is emitted and there is no `trust_bundle` manifest record; there is no implicit "every declared CA" bundle. This supersedes ADR-016's always-emit — declarative-over-implicit, so the config's output is exactly what it declares. A stable `pki.ca` path (the property ADR-016 wanted) is obtained by declaring a `trust_bundle` from day one, even single-member. Trade-off: configs that relied on the implicit `bundle.crt` must add a `trust_bundle` block (a behaviour change carried by a docs/changelog note, not a parse error).

See [ADR-026](../adr/026-trust-bundle-block.md) §2.

See [ADR-026](../adr/026-trust-bundle-block.md).

### D-12: `trust_bundle` `link_crt` closes the rotation fan-out gap

Per-CA `link_crt` (ADR-021) places a single CA cert, which is the wrong `pki.ca` content during a rotation. The bundle's own `link_crt`, with identical symlink semantics and the bundle-path basename as filename, keeps fanned-out directories correct before, during, and after rotation. Per-CA `link_crt` remains for consumers that deliberately pin one CA.

See [ADR-026](../adr/026-trust-bundle-block.md).

### D-13: `host` block renamed to `cert`, shipped first and in isolation

The per-certificate block is renamed `host`→`cert` so the keyword names the artifact the tool emits and encodes the scope boundary (it issues certs, it does not generate the Nebula daemon config). It is a mechanical breaking rename with no new signing behaviour, so it ships as its own release **first** — the later CA-reference and trust-bundle iterations then land on the final `cert` keyword, and examples/testdata are rewritten once, not twice.

Scope (decided 2026-09-26, experimental-stage posture per the ADR-007 amendment): no "host" naming for the per-certificate concept survives. The manifest map becomes `certs` without a `schema_version` bump; the default directory becomes `out/certs/`; code identifiers, CLI output and every ADR are swept, and ADR-009/017/020 are renamed with all links updated. There is no special parse error for `host` and no migration path; existing `out/` trees are regenerated. Full list in ADR-024 "Scope of the rename".

See [ADR-024](../adr/024-rename-host-to-cert.md).

## Iteration plan: v0.1.0 → v0.2.0

Each step ships as `v0.1.x`. Every step re-runs the full prior test suite.

### v0.1.1 — sops write path

- `internal/crypto/`: `Encryptor` interface, `NoneBackend`, `SopsBackend.Encrypt` (CLI subprocess).
- Config: `encryption "sops"` / `encryption "none"` decoded; wired through to `apply`.
